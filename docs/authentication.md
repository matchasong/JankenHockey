# 認証設計

当プロジェクトにおける認証設計の方針を記載する

## 要件

当プロジェクトはオンライン 2 人対戦ゲームであり。ゲームにおいて自分と相手のユーザーの識別が必要である。
そのため、下記の通り最低限のユーザー登録および認証機能を実装することとした。

- ユーザー登録機能

  - ユーザー名とパスワードによる登録  
    メールアドレス等での本人確認は、ユーザーの利便性を損なうため、実施しないこととした。
  - すでに登録済みのユーザー名との重複登録は不可とする  
    ゲーム画面での表示上名前が区別できなくなるため、同名ユーザーは登録試行時にエラーとする(Cognito ユーザープールの標準設定を利用)。

- ログイン機能

  - ユーザー名とパスワードによるログイン

- ログアウト機能

  - クライアント側でのトークン破棄によるログアウト

## 採用技術

- AWS Cognito ユーザープール

  当プロジェクトでは、AWS Cognito を認証基盤として採用した。当ゲームのバックエンドは AWS で開発していることから、相性が良いと考えた。  
  API Gateway V1(REST API)については、Cognito オーソライザによって、特段認証についてのコーディングをせずに、直接連携することが可能。  
  API Gateway V2(WebSocket)については、Cognito と直接連携できないため、下記の通り JWT を利用した認証を実装することとした。

- JWT (JSON Web Token)

  2 人対戦のゲーム中の通信は API Gateway V2(WebSocket)を利用して実装しているが、API Gateway V2 は Cognito と直接連携できない。  
  そこで、Lambda オーソライザにて JWT を用いた認証を実装することとした。  
  クライアントは、ログイン時に、取得した JWT トークンを ブラウザの session storage に保存する。
  API Gateway への接続時にトークンを送信し、Lambda オーソライザ側でトークンの検証を行うことで認証を実現する。  
  なお、WebSocket は一度確立した接続を維持するため、WebSocket 接続開始時にのみ認証を行ない、以降のメッセージ送信時には認証を行わない。

  ログアウト時に、ブラウザの session storage に保存したトークンを破棄する。

  Cognito ユーザープールが発行できる JWT トークンは下記の 3 種類である。  
  当プロジェクトでは、ユーザーの権限を付与する目的でアクセストークンおよび ID トークンを利用している。

  - アクセストークン

    ユーザーの権限情報を含むトークン。主に認可目的で利用される。  
    Lambda オーソライザで、ユーザーに WebSocket 呼び出しの権限を付与するために利用。  
    有効期限は Cognito ユーザープールのデフォルト設定値である 1 時間としている。

  - ID トークン

    ユーザーの属性情報を含むトークン。主に認可目的で利用される。  
    ユーザーに REST API 呼び出しの権限を付与するために利用。  
    (Cognito オーソライザが ID トークンを利用する仕様のため、REST API へのアクセスの認証についてのみ、アクセストークンではなく ID トークンを利用している)  
    有効期限は Cognito ユーザープールのデフォルト設定値である 1 時間としている。

  - リフレッシュトークン

    新しい ID トークンおよびアクセストークンを取得するためのトークン。当プロジェクトでは未使用。

## セキュリティ考慮

当プロジェクトでは、ユーザーの機密情報は保持しない。
また、ユーザーの対戦成績によるランク付などの機能もないため、複数アカウント保持の対策も不要と判断した。
また、特に SLA は設けていないため、対策としてサービス停止も許容することとした。

以上より、主なリスクは(D)DoS 攻撃による課金増加と考え、下記を対策する

- API Gateway のスロットリング設定

  API Gateway のスロットリング設定を行い、過剰なリクエストを防止する。

- API 呼び出し回数およびテーブルデータ容量に対する監視

  CloudWatch アラームを設定し、異常な増加があった場合に通知を受け取るようにする。

- AWS Budgets による費用上限設定

  AWS Budgets によって、月額費用の上限を設定し、一定金額到達時に通知を受け取るようにする。

- CloudFormation スタックによる環境構築

  インフラは CloudFormation スタックによって構築している。  
  事象が発生した場合には、Lambda 関数の呼び出し無効化やスタック削除により、課金の拡大を防止できるようにする。

## 今後の改善ポイント

可用性要件が厳しくなった場合、ユーザー数が増えた場合、保存するユーザー情報が増えた場合などには、認証設計の見直しを行うこととする。  
例えば、AWS Shild Advanced の導入による DDoS アクセス強化、AWS WAF の導入による不正アクセス防止、Cognito ユーザープールの設定による制御の強化(メールアドレス確認など)が考えられる。
