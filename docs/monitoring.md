# ログおよび監視設計

当プロジェクトにおけるログおよび監視設計の方針を記載する。

## 要件

DDoS 攻撃による課金増や、システムの障害検知および調査のため、下記のログおよび監視機能を要件とした。

- フロントエンドのロギング

  基本はログ出力を行わない。エラーについてのみ数箇所コンソール出力を行っている。

- バックエンドのロギング

  - Lambda 関数の実行ログ
  - API Gateway のアクセスログ

- 監視

  - API 呼び出しに対する監視およびメール通知
  - DynamoDB テーブルの監視およびメール通知
  - Lambda 関数の監視およびメール通知
  - 課金予実の監視およびメール通知

## 採用技術

- AWS CloudWatch Logs (バックエンドのロギング)

  バックエンドのログ出力については、AWS CloudWatch Logs を利用することとした。
  Lambda 関数の実行ログは、プログラム中で[logging](https://docs.python.org/ja/3.12/library/logging.html)モジュールを用いてログの標準化を図った。  
  API Gateway のアクセスログについては、CloudFormation テンプレートで設定を追加することで、CloudWatch Logs に出力されるようにした。

- AWS CloudWatch Alarm + AWS SNS (監視)

  監視については、AWS CloudWatch Alarm と AWS SNS を組み合わせて実現することとした。
  主要な API 呼び出しに対しては、WebSocket および RestAPI について、API レベルでの一定期間内の呼び出し回数制限を設け、超過した場合にアラームが発報されるように設定した。  
  また、API 配下の Lambda 関数に対しても呼び出し回数のアラームを設定した。  
  主要な DynamoDB テーブルについては、Room, Connection, GameHistory の各テーブルについて書き込み多発時にアラームが発報されるように設定した。  
  いずれのアラームも SNS トピックに通知されるように設定し、SNS トピックから監視担当者へメール通知が送信されるようにした。

## ログ設計

ログについての詳細な設計を以下に記載する。

### ログレベル

当プロジェクトでは、ログレベルを下記の通り定義する。

| レベル      | 用途                                                 | 具体例                                                     | 対応優先度             |
| ----------- | ---------------------------------------------------- | ---------------------------------------------------------- | ---------------------- |
| **ERROR**   | システムの一部または全部が正常に動作しない重大な問題 | ゲームの強制終了、システム側都合でログインやゲーム開始失敗 | 優先して対応           |
| **WARNING** | 潜在的な問題や注意が必要な状況。システムは継続可能   | ログイン失敗                                               | 頻発時に対応           |
| **INFO**    | システムの正常な動作に関する情報                     | Lambda 関数の開始・終了、処理の主要なポイント              | 原則対応は不要         |
| **DEBUG**   | 開発およびデバッグ時に有用な詳細情報                 | 変数の値、処理の内部状態                                   | (開発時のみ有効化する) |

基本的には INFO レベルでログを出力することとする。  
ただし、一部のプログラムについては、稼働の安定までは当面 DEBUG レベルで出力する。

### ログフォーマットおよびログの例

時刻(UTC 換算) - Lambda 名 - ログレベル - 関数名 - メッセージ が出力される。

```
2025-11-15 15:05:43 - create_room - INFO - handler - START create_room.py
```

### ログの保持期間

ログは無期限で保持する。なお CloudFormation や AWS コンソールから手動で保持期間の設定変更が可能。ログの手動削除は可能である。

### ログの暗号化

なお、機密情報は含まれないため、KMS キーを用いたログの暗号化は実施しない。(よりセキュリティ観点を重視するのであれば、別途設定を検討する。)

### ログ解析時の注意点

Lambda 関数の実行ログについては、時刻が **UTC 換算**になる点に注意すること。

## 監視設計

下記の監視を実施する。
詳細は monitoring.yaml の CloudFormation テンプレートを参照のこと。
1 ゲーム(1 分間)あたり 3000 回程度の WebSocket API 呼び出しが発生する想定で、同時に 2 ゲーム(同時接続 4 人)程度までを通常の負荷と想定している。

Lambda 関数の ERROR ログアラートは、アプリケーションのエラーログを検知してメール通知を行う。
課金抑制のため、複数の Lambda 関数を集約していることに注意。

| 監視対象                           | メトリクス     | 閾値                | 意図                     |
| ---------------------------------- | -------------- | ------------------- | ------------------------ |
| WebSocket API                      | 呼び出し回数   | 5 分あたり 30000 回 | DDoS 検知                |
| REST API                           | 呼び出し回数   | 5 分あたり 200 回   | DDoS 検知                |
| Lambda 関数（WebSocket 接続）      | 呼び出し回数   | 1 分あたり 10 回    | 大量 API 呼び出し検知    |
| Lambda 関数（WebSocket default）   | 呼び出し回数   | 1 分あたり 7000 回  | 大量 API 呼び出し検知    |
| Lambda 関数（WebSocket 切断）      | 呼び出し回数   | 1 分あたり 10 回    | 大量 API 呼び出し検知    |
| Lambda 関数（REST API 全 7 関数）  | ERROR ログ出力 | 1 分あたり 1 回以上 | エラー発生検知           |
| Lambda 関数（WebSocket 全 4 関数） | ERROR ログ出力 | 1 分あたり 1 回以上 | エラー発生検知           |
| DynamoDB: Room                     | 書き込み回数   | 1 分あたり 20 回    | 大量ルーム作成検知       |
| DynamoDB: Connection               | 書き込み回数   | 1 分あたり 20 回    | 接続増加検知             |
| DynamoDB: GameHistory              | 書き込み回数   | 1 分あたり 5 回     | ゲーム履歴の異常増加検知 |
| Budgets: 予算(月間$10)の 80%       | 月間予算の実績 | 予算(月間$10)の 80% | 予算超過の防止           |
| Budgets: 予算(月間$10)             | 月間予算の実績 | 予算(月間$10)       | 予算超過の防止           |
| Budgets: 予算(月間$10)の予測値     | 月間予算の予測 | 予算(月間$10)       | 予算超過の防止           |

📝 Budgets のアラートを有効にするためには、AWS マネジメントコンソールより、コスト配分タグ「Project」の有効化が必要。

## 今後の改善ポイント

- 監視アラーム数
  現状では CloudWatch Alarm の課金の制約から、無料枠上限の 10 個に収まるようにしている(API 呼び出し 2 個、主要な Lambda 関数実行回数 3 個、主要な DynamoDB テーブル 3 個、エラーログ監視 2 個の計 10 個。なお、Budgets アラートは CloudWatch Alarm ではないためこの数に含まれない。)。  
  月次のレポートで確認し、必要に応じてアラーム数の増加を検討する。  
  スロットリングに対するアラートについては、頻発するようであれば設定を検討する。
